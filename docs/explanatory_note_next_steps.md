# Подальший план роботи над пояснювальною запискою

## 1. Що писати першим

1. **Вступ**  
   Написати актуальність, мету, завдання, об’єкт, предмет, методи дослідження і практичну цінність. Це задасть логіку всієї роботи.

2. **Розділ 1**  
   Описати предметну область: ритейл, попит, фактори попиту, проблему прогнозування, огляд методів і концепцію системи.

3. **Розділ 2**  
   Описати вимоги, структуру даних, SQLite, архітектуру, алгоритми та питання санкціонованого доступу.

4. **Розділ 3**  
   Описати реалізацію Flask-застосунку, CSV-імпорт, ML-модулі, прогноз, метрики, тестування та результати.

5. **Висновки**  
   Писати після завершення трьох розділів, щоб вони відповідали реальним результатам.

## 2. Які скріншоти вставити

У розділ 1:
- `огляд.png` — загальний вигляд системи;
- схема проблемної ситуації в ритейлі.

У розділ 2:
- `дані.png` — структура набору даних;
- `імпорт.png` — імпорт CSV;
- схема архітектури;
- ER-схема SQLite.

У розділ 3:
- `прогноз.png` — графік історії та прогнозу;
- `модель.png` — метрики та порівняння моделей;
- `про систему.png` — сторінка опису системи;
- скріншот результату тестів або фрагмент консолі з `pytest`.

## 3. Які схеми треба зробити

1. **Схема проблемної ситуації**  
   Історичні продажі → фактори попиту → складність ручного аналізу → потреба в прогнозі.

2. **Концептуальна схема системи**  
   CSV → preprocessing → feature engineering → ML model → forecast → web interface.

3. **ER-схема бази даних SQLite**  
   `products`, `sales`, `forecasts`, `model_metrics`, `imports`, `users`.

4. **Блок-схема алгоритму прогнозування**  
   Вибір товару → отримання історії → формування ознак → модель → прогноз → графік і висновок.

5. **Схема оцінки якості моделі**  
   Train/test split → predictions → MAE/RMSE/MAPE → model comparison → ExtraTreesRegressor.

## 4. Що узгодити з керівником

- Чи потрібно у фінальній записці планувати 30 або 40 джерел. Рекомендовано 40 через критерії методичних рекомендацій.
- Як саме описувати санкціонований доступ: як поточну відкриту демонстрацію з можливістю додавання авторизації.
- Чи залишати згадку про таблицю `recommendations` у базі даних, якщо інтерфейс не робить закупівлі головним фокусом.
- Чи потрібен окремий економічний ефект або достатньо практичної цінності для ритейлу.
- Чи включати повні фрагменти коду в додатки або лише ключові частини.

## 5. Що перевірити перед здачею

- Назва теми всюди однакова.
- Мета, об’єкт і предмет збігаються із завданням.
- У тексті не перебільшено можливості системи.
- Не написано, що система автоматично керує закупівлями, цінами, маркетингом або логістикою.
- Усі рисунки мають номери й підписи.
- Усі таблиці мають номери й назви.
- Усі джерела оформлені за вимогами кафедри.
- У списку джерел не менше 30 позицій, краще 40.
- Є посилання на рисунки, таблиці, формули й додатки.
- Додатки містять схеми, скріншоти, фрагменти коду та SQL-схему.
- Команди `py -m compileall app src`, `py -m pytest`, `py app/app.py` проходять перед демонстрацією.
