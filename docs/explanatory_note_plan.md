# План пояснювальної записки до кваліфікаційної бакалаврської роботи

Тема: «Розробка інтелектуальної системи прогнозування попиту на товари для автоматизації процесів ритейлу».

План складено на основі індивідуального завдання, методичних рекомендацій, поточного Flask/ML-проєкту Retail Demand Sense, README, docs-файлів і наявних скріншотів інтерфейсу.

## 1. Загальний обсяг і структура

Індивідуальне завдання вимагає 80–90 сторінок без додатків, шрифт 14, інтервал 1,5. У завданні зазначено не менше 30 джерел, але методичні рекомендації в критеріях оцінювання вказують мінімум 40 джерел і бажано 70% нової літератури за останні 10 років. Безпечний варіант — планувати 40 джерел.

Орієнтовний розподіл:

| Частина | Орієнтовний обсяг |
| --- | ---: |
| Титульні елементи, завдання, реферат, зміст, перелік скорочень | не входять або частково входять за правилами кафедри |
| Вступ | 5–7 стор. |
| Розділ 1. Аналіз предметної області та концепція системи | 22–25 стор. |
| Розділ 2. Проєктування системи та питання програмної інженерії | 24–27 стор. |
| Розділ 3. Реалізація, тестування та результати роботи системи | 27–30 стор. |
| Висновки | 3–4 стор. |
| Список джерел | за фактичним обсягом |
| Разом без додатків | 80–90 стор. |

## 2. Вступ

Орієнтовно: 5–7 сторінок.

Що писати:
- актуальність прогнозування попиту в ритейлі;
- проблема ручного аналізу продажів і неточного планування;
- роль ML у прогнозуванні попиту;
- зв’язок теми з автоматизацією процесів ритейлу;
- мета роботи;
- завдання роботи;
- об’єкт і предмет дослідження;
- методи дослідження;
- практичне значення;
- короткий опис структури пояснювальної записки.

Підтверджено проєктом:
- є web-система прогнозування попиту;
- є CSV-імпорт, SQLite, ML-модель, метрики й сторінки інтерфейсу.

Обережно:
- не писати, що система вже впроваджена в реальному магазині;
- не писати, що вона автоматично керує запасами, цінами, маркетингом або логістикою;
- правильно формулювати: прогноз може підтримувати такі рішення, але не виконує їх автоматично.

## 3. Розділ 1. Аналіз предметної області та концепція системи

Орієнтовно: 22–25 сторінок.

### 1.1. Предметна область ритейлу та попиту на товари
Пояснити, що таке попит у ритейлі, чому він змінюється, які фактори впливають на продажі: сезонність, ціна, акції, день тижня, залишки, постачання, категорія товару.

Схеми/ілюстрації:
- схема факторів, що впливають на попит;
- скріншот головної сторінки `огляд.png` як приклад системи.

### 1.2. Проблемна ситуація
Описати проблему: менеджеру складно вручну аналізувати великі обсяги історії продажів, порівнювати товари, враховувати сезонність і оцінювати майбутній попит.

Графічні матеріали:
- схема проблемної ситуації: історичні продажі → багато факторів → потреба в прогнозі → управлінське рішення.

### 1.3. Огляд підходів до прогнозування попиту
Описати класичні статистичні підходи, часові ряди та ML-підходи. Пояснити, чому для дипломного прототипу обрано supervised learning/regression.

Обережно:
- не стверджувати, що використано ARIMA, Prophet або нейронні мережі, якщо їх немає в коді;
- можна згадувати їх лише як альтернативи в огляді.

### 1.4. Машинне навчання для задач прогнозування
Пояснити regression task, train/test split, feature engineering, метрики MAE/RMSE/MAPE.

Підтверджено кодом:
- `src/train_model.py`;
- `src/feature_engineering.py`;
- `models/metrics.json`;
- сторінка `Модель`.

### 1.5. Концепція розробленої системи
Описати ідею Retail Demand Sense: CSV-дані → preprocessing → ознаки → ML-модель → прогноз → web-інтерфейс.

Схеми:
- концептуальна схема системи;
- архітектурний flow зі сторінки `Про систему`.

## 4. Розділ 2. Проєктування системи та питання програмної інженерії

Орієнтовно: 24–27 сторінок.

### 2.1. Вимоги до системи
Описати функціональні вимоги:
- імпорт CSV;
- перегляд набору даних;
- побудова прогнозу;
- перегляд метрик;
- перегляд опису системи;
- API для прогнозу, метрик і стану системи.

Нефункціональні вимоги:
- локальний запуск;
- швидке відкриття сторінок;
- адаптивний web-інтерфейс;
- зрозумілі українські тексти;
- відсутність важких frontend-бібліотек;
- можливість подальшого додавання авторизації.

Підтверджено:
- routes у `app/app.py`;
- тести в `tests/`;
- docs/user_manual.md.

### 2.2. Структура вхідних даних
Описати CSV-поля:
- `date`;
- `product_id`;
- `product_name`;
- `category`;
- `sales_quantity`;
- `price`;
- `stock_quantity`;
- `promo`;
- `holiday`;
- `supplier_delay_days`;
- додаткові поля.

Скріншоти:
- `дані.png`;
- `імпорт.png`.

Підтверджено:
- сторінка `Дані`;
- `data/README.md`;
- `src/data_processing.py`.

### 2.3. Структура бази даних SQLite
Описати таблиці: `users`, `products`, `sales`, `forecasts`, `model_metrics`, `imports`, `recommendations`.

Обережно:
- таблиця `recommendations` є в структурі бази, але інтерфейс не позиціонується як система закупівель;
- її можна подати як службову/резервну таблицю для подальшого розвитку, якщо це узгоджено з керівником.

Схеми:
- ER-схема SQLite;
- фрагмент SQL-схеми в додатку.

Підтверджено:
- `src/database.py`;
- `docs/database_schema.sql`;
- `docs/database_description.md`.

### 2.4. Архітектура програмної системи
Описати:
- Flask backend;
- Jinja2 templates;
- static CSS/JS;
- ML-модулі в `src`;
- SQLite;
- API endpoints;
- Canvas-графіки.

Схеми:
- CSV → Обробка → Ознаки → ML-модель → API прогнозу → Web-інтерфейс.

### 2.5. Алгоритм роботи системи
Описати послідовність:
1. завантаження CSV;
2. перевірка даних;
3. очищення й нормалізація;
4. feature engineering;
5. навчання моделей;
6. вибір моделі;
7. генерація прогнозу;
8. відображення результату.

Схеми:
- блок-схема алгоритму імпорту;
- блок-схема алгоритму прогнозування.

### 2.6. Питання санкціонованого доступу
Писати обережно:
«У поточній демонстраційній версії доступ до інтерфейсу відкритий для зручності захисту. Архітектура системи дозволяє додати авторизацію користувачів і розмежування ролей».

Не писати:
- що всі сторінки зараз захищені авторизацією;
- що є повноцінна рольова модель, якщо вона не використовується в основному UI.

## 9. Обережні формулювання

Не перебільшувати:
- система не є production ERP/POS;
- система не виконує автоматичну закупівлю;
- система не керує цінами автоматично;
- система не запускає маркетингові кампанії;
- система не виконує логістичну оптимізацію;
- авторизація описана як можливість розвитку, а не як центральна функція поточної демонстрації.

Коректні формулювання:
- «може використовуватися для підтримки рішень»;
- «прогноз може бути основою для планування запасів»;
- «ціна, акції та логістичні характеристики можуть бути ознаками моделі»;
- «поточна версія є програмною реалізацією для демонстрації підходу».
